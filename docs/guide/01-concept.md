# Daedalus 핵심 컨셉

Daedalus는 Claude Code 플러그인을 **그림으로 설계하고, 파일은 컴파일러가 쓰게 하는** 도구입니다.
이 문서는 "왜 이렇게 만들었고, 무엇을 그리면 무엇이 나오는지"를 한 번에 잡는 입문서입니다.

함께 보면 좋은 문서:

- [로컬 vs 마켓플레이스 플러그인](04-local-vs-marketplace.md) — 빌드 타깃 차이
- [로컬 전용 기능](05-local-only-features.md) — 로컬 빌드에서만 되는 것들

## 1. 어떤 문제를 푸나

플러그인이 조금만 커져도 파일이 여러 개가 됩니다. 스킬 A가 끝나면 스킬 B를 부르고,
실패하면 에이전트 C에게 맡기고, C가 끝나면 다시 D로 가고…

이걸 손으로 쓰면 이런 일이 생깁니다.

- A의 SKILL.md에 "다음은 B"라고 썼는데, B 이름을 바꾸고 A는 안 고쳤다.
- B는 "A에서 왔다"는 걸 모르고 처음부터 다시 시작한다.
- 에이전트 이름에 오타가 있어도 Claude Code는 **아무 말 없이** 넘어간다.
- 세션이 끊기면 어디까지 했는지 아무도 모른다.

Daedalus에서는 **그래프(그림)가 원본**입니다. 스킬과 에이전트를 노드로 놓고 선으로 잇습니다.
"다음은 누구", "어디서 왔나", "어디까지 했나" 같은 연결 문구는 **컴파일러가 그래프를 보고 써 줍니다**.
이름을 바꾸면 모든 파일이 다시 컴파일될 때 함께 바뀝니다.

## 2. 흐름: 모델 → 컴파일러 → 플러그인 파일

```
캔버스에 그린 그래프 + 각 컴포넌트의 설정·본문   (모델)
              │
              ▼   Ctrl+B
          컴파일러  ── 검증 통과해야 진행
              │
              ▼
  SKILL.md · 에이전트 .md · 훅 · 블랙보드 스키마 · plugin.json …
```

- 여러분이 편집하는 것은 **모델**입니다. 산출된 `.md` 파일을 직접 고치지 마세요. 다음 컴파일 때 덮어씁니다.
- 같은 모델은 언제나 **같은 텍스트**로 나옵니다. 그래서 git diff로 변화를 보기 쉽습니다.
- 컴파일러가 **자동으로 쓰는 문구는 영어**입니다(모든 스킬에 반복해서 실리므로 토큰을 아끼려고).
  여러분이 쓴 본문·설명은 한국어든 영어든 그대로 나갑니다.

## 3. 기본 재료

### 프로젝트 그래프

**Project FSM** 탭의 캔버스가 곧 워크플로입니다.

| 그림 요소 | 뜻 |
|-----------|-----|
| **노드** | 워크플로의 한 단계. 스킬이나 에이전트를 끌어다 놓으면 노드가 됩니다 |
| **출력 포트** | 그 단계가 끝나는 방식(갈래). 예: `done`, `failed`, `needs_review` |
| **전이(선)** | "이 갈래로 끝나면 저기로 간다". 어느 포트에서 나가는지가 곧 **트리거**입니다 |
| **가드** | 전이에 붙이는 추가 조건. 자연어로 씁니다 (예: "테스트가 전부 통과했을 때") |
| **호출 포트** | 에이전트에게 일을 맡기는 출구. 에이전트로 가는 선은 여기서만 나갑니다 |

선만 그어서는 갈래가 생기지 않습니다. 갈래가 둘 이상이면 노드에 출력 포트를 선언하고, 각 포트에서 선을 따로 뽑으세요.

### 컴포넌트 종류

| 종류 | 한 줄 설명 |
|------|-----------|
| 절차형 스킬 | 작업 지침. 워크플로의 단계로 가장 많이 씁니다 |
| fork 스킬 | 절차형과 같지만, 본문이 **서브에이전트(fork 에이전트)** 에서 실행됩니다 |
| 선언형 스킬 | 배경 지식. 에이전트에게 자동으로 실립니다 |
| 전이 스킬 | 선 위에 올리는 짧은 중간 단계 (A→B 사이에 "먼저 이것부터") |
| 참조 스킬 | 참조 문서. 여러 노드에 링크할 수 있습니다 |
| 랩핑 스킬 | 다른 플러그인의 스킬을 감싸 내 워크플로의 단계로 씁니다 |
| 에이전트 | 별도 컨텍스트에서 일하는 작업자. 절차는 본문에, 결과 갈래는 출력 포트로 |

각 종류의 필드와 쓰임새는 [02-registry.md](02-registry.md))에 자세히 있습니다.

## 4. FSM + 블랙보드: 왜 이렇게 나눴나

### 워크플로는 상태 기계(FSM)다

FSM(Finite State Machine, 유한 상태 기계)은 "지금 어느 단계에 있고, 무슨 일이 생기면 어디로 가는가"를
표로 적은 것입니다. 플러그인 워크플로가 딱 그 모양입니다.

- **지금 어디?** → 노드
- **무슨 일이 생기면?** → 출력 포트(트리거) + 가드
- **어디로?** → 전이

이렇게 적어 두면 "갈 곳 없는 갈래", "아무도 오지 않는 노드" 같은 구멍을 도구가 찾아 줄 수 있습니다.

참고로 Daedalus가 워크플로를 **직접 실행하지는 않습니다**. 실제로 움직이는 건 Claude Code이고,
그래프는 컴파일되어 각 파일의 지시문("이게 끝나면 B를 부르라")이 됩니다.

### 블랙보드는 컨텍스트 사이의 공유 메모다

스킬 A와 B가 **같은 대화** 안에서 이어진다면 A가 한 일을 B도 이미 압니다. 이때는 블랙보드가 필요 없습니다.

하지만 에이전트나 fork 스킬은 **다른 컨텍스트**에서 돕니다. 세션이 끊겼다가 다시 시작할 때도 기억이 없습니다.
이럴 때 파일로 데이터를 넘기는 장치가 블랙보드입니다.

1. **설계할 때** — 블랙보드 탭에서 클래스와 필드를 정합니다. 예: `Review` 클래스에 `issues`(문자열 목록), `approved`(bool).
2. **각 노드에 접근을 선언** — 이 단계는 `Review.issues`를 **쓴다**, 저 단계는 **읽는다**. 캔버스에 ✏/📖 뱃지가 붙습니다.
3. **컴파일** — 스키마 파일(`schemas/<플러그인>.json`)이 나오고, 각 스킬 본문에 "무엇을 읽고 쓰는지"가 적힙니다.
4. **실행할 때** — 상태는 작업 폴더의 `state/<플러그인>/<클래스>.json`에 저장됩니다.

읽고 쓰기는 `daedalus-bb` 명령이 맡습니다. Daedalus를 설치하면 함께 깔립니다.

```bash
daedalus-bb --schemas <스키마 경로> write Review --append issues="로그인 버튼 누락"
daedalus-bb --schemas <스키마 경로> read Review --field approved
```

Claude가 JSON을 손으로 만들면 형식을 어기기 쉽습니다. `daedalus-bb`는 쓰기 전에 스키마로 검사하고
(틀리면 파일을 바꾸지 않습니다), 파일을 한 번에 바꿔 써서 도중에 끊겨도 깨지지 않게 합니다.

**언제 쓰나 / 안 쓰나**

| 쓰세요 | 쓰지 않아도 됩니다 |
|--------|-------------------|
| 에이전트·fork 스킬에 데이터를 넘길 때 | 같은 대화 안에서 스킬끼리 이어질 때 |
| 세션이 끊겨도 남아야 하는 결과 | 한 단계 안에서만 쓰고 버리는 값 |
| 여러 단계가 같은 목록을 함께 채울 때 | 그냥 "무엇을 했는지" 한 줄 메모 (진행 기록의 `note`로 충분) |

클래스 설계·접근 선언·CLI·관련 경고는 [블랙보드](03-blackboard.md)에서 자세히 다룹니다.

## 5. 컴파일러가 대신 써 주는 것

아래 단락은 **여러분이 쓰지 않아도** 산출 파일에 자동으로 붙습니다. 모두 그래프에서 계산됩니다.

| 자동 단락 | 들어가는 곳 | 하는 일 |
|-----------|-------------|---------|
| Next Steps (다음 단계) | 스킬 | 갈래별로 다음에 부를 스킬·맡길 에이전트. 출력 포트 설명도 함께 |
| Resuming Work (작업 재개) | 스킬 | 시작할 때 진행 기록을 확인해 이어서 할지 판단 |
| 진행 기록 갱신 | 스킬 | 끝날 때 `state/__progress__.json`에 완료·현재 위치·온 갈래를 남김 |
| Entry Context (진입 맥락) | 스킬 | "어느 스킬에서, 어떤 갈래로 왔으면 이렇게 하라" |
| Invocation Contract (호출 계약) | 에이전트 | 누가, 어떤 포트로, 무엇을 넘기며 부르는지 |
| Exits (출구) | 에이전트 | 완료 보고 첫 줄에 어느 출구로 끝났는지 적으라는 지시 |
| Shared State (블랙보드) | 스킬·에이전트 | 읽고 쓸 클래스와 `daedalus-bb` 사용법 |
| Report (보고) | 배치된 fork 스킬 | 서브에이전트가 보고할 형식. 다음 단계는 부른 쪽이 실행 |

그래서 여러분이 본문에 쓸 것은 **"이 단계에서 실제로 할 일"** 뿐입니다.
연결 문구를 본문에 또 쓰면 같은 말이 두 번 실리니 피하세요.

세션이 새로 시작될 때 진행 기록을 자동으로 보여 주는 훅도 기본으로 붙습니다(프로젝트 속성에서 끌 수 있습니다).

## 6. 검증과 되돌리기

### 검증 — 에러는 막고, 경고는 알린다

`F7`로 검증 결과를 봅니다. 항목을 누르면 문제 노드로 이동합니다.

- **에러** — 컴파일을 막습니다. 한 건이라도 있으면 파일을 **하나도 쓰지 않습니다**.
  예: 선이 없는 노드를 가리킴, 같은 스킬을 두 번 배치, 에이전트 호출이 너무 깊음.
- **경고** — 컴파일은 되지만 알아 두어야 할 것.
  예: 워크플로 중간 노드인데 사용자가 `/스킬`로 바로 시작할 수 있음, 아무도 안 쓰는 블랙보드 필드.

이름 규칙(소문자·숫자·하이픈)은 편집 중에는 경고지만, 컴파일할 때는 에러로 바뀝니다. 파일 이름이 되기 때문입니다.

### 되돌리기 — 편집은 거의 다 Ctrl+Z

노드 추가·삭제·이동, 선 연결, 필드 변경, 훅 같은 편집은 `Ctrl+Z`로 되돌릴 수 있습니다.
**예외: GUI의 블랙보드 탭과 속성 패널의 reads/writes 입력은 아직 되돌릴 수 없습니다**(바로 모델에 기록됩니다).
MCP로 한 블랙보드 편집은 되돌릴 수 있습니다 — 자세한 내용은 [블랙보드](03-blackboard.md).
여러 값을 한꺼번에 바꾼 조작(예: 진입점 프리셋)은 한 번에 되돌아갑니다.
본문 텍스트는 컴포넌트마다 자기 되돌리기 기록을 따로 갖습니다.

되돌릴 수 **없는** 것: 저장·열기 같은 파일 작업, 노드 선택.

## 7. 편집하는 두 가지 방법: GUI와 MCP

- **GUI** — 캔버스에 끌어다 놓고, 편집기 탭에서 필드와 본문을 채웁니다.
- **앱 내장 MCP 서버** — Daedalus를 켜면 MCP 서버가 함께 뜹니다. Claude Code를 연결하면
  "리뷰 단계 하나 추가해 줘"처럼 말로 같은 프로젝트를 편집할 수 있습니다.

둘은 **같은 프로젝트, 같은 되돌리기 기록**을 씁니다. Claude가 만든 노드는 화면에 바로 나타나고,
마음에 안 들면 `Ctrl+Z`로 지우면 됩니다. GUI로 되는 일은 MCP로도 됩니다.
자세한 사용법은 [06-mcp.md](06-mcp.md)), 도구 전체 목록은 [`docs/MCP.md`](../MCP.md)에 있습니다.

## 8. 빌드 타깃

컴파일 결과를 어디에 어떤 모양으로 낼지 고릅니다.

- **마켓플레이스**(기본) — `plugin.json`이 있는 배포용 플러그인 폴더를 만듭니다.
- **로컬** — 대상 작업 폴더의 `.claude/`에 바로 넣습니다. **컴파일이 곧 설치**입니다.
  MCP 서버·훅·권한 모드를 쓰는 에이전트는 마켓플레이스 플러그인에서 Claude Code가 무시하므로, 이런 에이전트는 로컬로 만듭니다.

차이는 [04-local-vs-marketplace.md](04-local-vs-marketplace.md)), 로컬에서만 되는 기능은 [05-local-only-features.md](05-local-only-features.md))를 보세요.

## 9. 따라 해 보기: 3단계 코드 리뷰 워크플로

"코드 작성 → 리뷰 → (문제 있으면) 수정" 흐름을 만들어 봅니다.

**① 컴포넌트 만들기**

| 이름 | 종류 | 출력 포트 |
|------|------|-----------|
| `write-code` | 절차형 스킬 | `done` |
| `reviewer` | 에이전트 | `approved`, `changes_requested` |
| `fix-code` | 절차형 스킬 | `done` |

에이전트는 호출 포트로만 부를 수 있으니, `write-code`와 `fix-code`에 `reviewer`를 부르는 호출 포트를 하나씩 추가합니다.

**② 캔버스에 놓고 잇기**

```
write-code ──(호출)──▶ reviewer ──approved──────────▶ (끝)
                          │
                          └──changes_requested──▶ fix-code ──(호출)──▶ reviewer
```

`write-code`는 진입점 프리셋 "진입점으로"를 골라 사용자가 `/write-code`로 시작할 수 있게 합니다.
`fix-code`는 중간 단계이니 "순수 상태로"를 고릅니다(안 하면 경고가 뜹니다).

**③ 블랙보드 (선택)**

리뷰어가 찾은 문제를 `fix-code`가 받아야 합니다. 둘은 컨텍스트가 다르니 블랙보드가 맞습니다.

- 클래스 `Review`, 필드 `issues`(문자열 목록)
- `reviewer` 노드: `Review.issues` 쓰기 / `fix-code` 노드: `Review.issues` 읽기

**④ 본문 쓰기**

각 본문에는 할 일만 씁니다. 예: `reviewer` 본문 — "변경된 파일을 읽고 버그·누락을 찾는다. 문제가 없으면 approved로 끝낸다."
"끝나면 fix-code로 가라" 같은 문장은 쓰지 않습니다.

**⑤ 검증하고 컴파일**

`F7`로 에러가 없는지 보고 `Ctrl+B`로 컴파일합니다. `write-code`의 SKILL.md 끝에는 대략 이런 단락이 붙어 있을 겁니다.

```markdown
## Next Steps
When this skill is done, continue the workflow by the matching branch:
- [...] → delegate to agent `reviewer`, after the agent returns: ...
```

`reviewer.md`에는 누가 부르는지(Invocation Contract)와 두 출구(Exits)가,
`fix-code`의 SKILL.md에는 "reviewer에서 changes_requested로 들어왔다"는 진입 맥락과 `Review.issues`를 읽는 방법이 들어갑니다.
이 중 어느 것도 여러분이 직접 쓰지 않았습니다.

## 정리

- 그래프가 원본이고, 파일은 컴파일러가 씁니다.
- 노드는 단계, 출력 포트는 갈래, 선은 "이 갈래면 저기로".
- 다른 컨텍스트로 데이터를 넘길 때만 블랙보드를 씁니다.
- 연결 문구·진행 기록·호출 계약은 자동입니다. 본문엔 할 일만.
- 에러가 있으면 컴파일되지 않고, 편집은 대부분 되돌릴 수 있습니다(GUI 블랙보드 편집은 예외).
